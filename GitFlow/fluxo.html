Fluxo GitFlow

Tudo nasce de production. Features são testadas em staging (opcional), só as aprovadas entram na release/vX.Y.Z por squash, a release vai para production por PR e ganha uma tag. Depois, staging é resetada. A cada N releases (padrão 2), main recebe o backup estável por PR de production, o único caminho até ela.

Fluxo regular

Clique em um número no diagrama ou no título de um passo para destacá-lo.

production release/v* feature/* staging main (backup) reset de staging

Sem homologação: pule os passos 2, 5 e 7. O backup em main (passo 8) é igual nos dois casos.

Quem faz o quê

Dev e QA

  • Criam feature/*, bugfix/*, chore/* a partir de production
  • Fazem merge em staging para teste
  • QA aprova ou reprova cada feature
  • Abrem o PR squash da feature aprovada para a release

Mantenedor (ou agente autorizado)

  • Cria release/vX.Y.Z a partir de production
  • Reseta staging e abre o PR da release para production
  • Cria a tag anotada vX.Y.Z
  • A cada N releases, abre o PR production → main
  • Agente autorizado por padrão; /conventions release off revoga

GitHub Actions

  • pr-checks, ci, security nos PRs
  • staging.yml no push de staging
  • release.yml no push da tag: valida, testa, empacota, atesta, publica, faz deploy e avisa quando é hora do backup em main
  • Nunca cria branches nem tags

Passos e verificação

1

Desenvolvimento

Dev executa
git fetch origin
git switch -c feature/proj-123-export-csv origin/production
git commit -m "feat(proj-123): adiciona exportação em CSV"
git push -u origin feature/proj-123-export-csv
# atualizar: git rebase origin/production (nunca staging)

2

Teste em homologação

opcional
Dev executa
git fetch origin
git switch staging
git reset --hard origin/staging
git merge --no-ff feature/proj-123-export-csv
git push origin staging
gh run watch
Actions
  • staging.yml: CI, pacote staging-<sha>, deploy em homologação
Conferir
3

Corte da release

Mantenedor executa
git fetch origin --tags
git describe --tags --abbrev=0 --match 'v[0-9]*' origin/production
VERSION=v1.4.0
git push origin "origin/production:refs/heads/release/$VERSION"
Conferir
4

Features aprovadas por squash

Dev ou mantenedor executa
gh pr create --base "release/$VERSION" --head feature/proj-123-export-csv \
  --title "feat(proj-123): adiciona exportação em CSV"
gh pr checks feature/proj-123-export-csv --watch
gh pr merge feature/proj-123-export-csv --squash

Reprovadas não abrem PR. Para tirar uma que já entrou: chore/* a partir da release com git revert <commit-do-squash> e PR para ela.

Conferir
5

Validação final

opcional
Mantenedor executa
git fetch origin
git push --force-with-lease origin "origin/release/$VERSION:staging"
gh run watch
git cliff --bumped-version "origin/production..origin/release/$VERSION"
Conferir
6

Publicação

Mantenedor executa
gh pr create --base production --head "release/$VERSION" \
  --title "chore(release): publica $VERSION"
gh pr checks "release/$VERSION" --watch
gh pr merge "release/$VERSION" --merge --delete-branch
git fetch origin --tags
git tag -a "$VERSION" origin/production -m "Release $VERSION"
git push origin "$VERSION"
gh run watch
Actions — release.yml
  • Tag anotada, contida em production, maior que a anterior
  • CI, pacote, atestação, GitHub Release, deploy em production
Conferir
7

Reset de staging

opcional
Mantenedor executa
git fetch origin
git push --force-with-lease origin origin/production:staging
Conferir
8

Backup estável em main

A cada N releases (padrão 2)
git fetch origin --tags
git tag -l 'v[0-9]*' --merged origin/production --no-merged origin/main
gh pr create --base main --head production \
  --title "chore(release): backup estável $VERSION"
gh pr checks production --watch
gh pr merge production --merge

Único caminho até main. Intervalo em .claude/conventions.json (/conventions main-sync <n>); o release.yml avisa quando chega a vez.

Conferir

Fluxo de hotfix

Correção urgente vai direto para production por PR, sem release e sem passar por staging antes.

1 · Hotfix a partir de production
git fetch origin --tags
git switch -c hotfix/cve-2026-1234 origin/production
git commit -m "fix(auth): corrige validação de token expirado"
git push -u origin hotfix/cve-2026-1234
2 · PR squash e tag de patch
gh pr create --base production --title "fix(auth): corrige validação de token expirado"
gh pr checks hotfix/cve-2026-1234 --watch
gh pr merge hotfix/cve-2026-1234 --squash --delete-branch
git fetch origin --tags
last=$(git describe --tags --abbrev=0 --match 'v[0-9]*' origin/production)
IFS=. read -r major minor patch <<< "${last#v}"
VERSION="v$major.$minor.$((patch + 1))"
git tag -a "$VERSION" origin/production -m "Hotfix $VERSION"
git push origin "$VERSION"
3 · Levar para staging
git switch staging && git reset --hard origin/staging
git cherry-pick origin/production
git push origin staging

O hotfix conta como release para o intervalo do backup em main (passo 8). Se houver release aberta, leve o fix para ela com bugfix/* a partir de production e PR squash.

ProteçãoRegraImpede
